# link-tracker

[![CI](https://github.com/NKorshunov19/link-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/NKorshunov19/link-tracker/actions/workflows/ci.yml)

Учебный проект: сервис следит за репозиториями на GitHub и сообщает подписчику, когда
там появились новые коммиты. Подписку добавляют через REST, дальше планировщик сам
обходит ссылки и опрашивает GitHub.

Тему взял по мотивам учебного проекта Т-Банка «Link Tracker». Таблица со ссылками и три
ручки пишутся за вечер, а вся сложность в том, что внешний API ненадёжен и ограничен по
числу запросов: отвечает 403 или 429 на лимите, иногда 500, иногда просто молчит, а
репозиторий за это время могли удалить. Почти весь код о том, как на это реагировать.

Стек: Java 21, Spring Boot 3.5, PostgreSQL, Liquibase, RestClient, Spring Data JPA,
JUnit 5, WireMock, Docker, GitHub Actions. Тесты идут на H2 в режиме PostgreSQL.

## Запуск

```bash
mvn test                      # 74 теста, база, докер и интернет не нужны
docker compose up --build     # приложение вместе с PostgreSQL
```

Токен GitHub не обязателен, но без него лимит 60 запросов в час на IP вместо 5000.
Если он есть, `docker compose` подхватит его из переменной `GITHUB_TOKEN`.

```bash
curl -X POST localhost:8080/api/links -H 'Content-Type: application/json' \
  -d '{"subscriber":"nikita","url":"https://github.com/spring-projects/spring-boot"}'

curl 'localhost:8080/api/links?subscriber=nikita'

curl -X DELETE 'localhost:8080/api/links/1?subscriber=nikita'
```

Уведомления сейчас уходят в лог приложения, там их и видно.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | /api/links | добавить репозиторий, отдаёт 201 |
| GET | /api/links?subscriber= | подписки одного подписчика |
| DELETE | /api/links/{id}?subscriber= | отписаться, отдаёт 204 |
| GET | /actuator/health | состояние приложения |

Ссылка не вида `https://github.com/owner/repo` даёт 400, повторная подписка на тот же
репозиторий 409, чужая ссылка 404. Ошибки в формате ProblemDetail.

## Как устроено

Пакеты по смыслу: `github` про внешний API, `link` про модель подписки и REST, `poll` про
планировщик и обработку одной ссылки, `notify` про доставку, `common` про ошибки и `Clock`.
Схему ведёт Liquibase, Hibernate стоит в `ddl-auto: validate`, так что сущность,
разъехавшаяся с миграцией, не даст приложению подняться.

### ETag и лимит GitHub

Если раз в полминуты проверять сотню репозиториев, лимит без токена кончится за минуты.
Поэтому ETag прошлого ответа лежит в таблице рядом со ссылкой и в следующий раз уходит
в заголовке `If-None-Match`. На неизменившийся репозиторий GitHub отвечает 304, такой
ответ не тянет тело и не тратит лимит. В тесте WireMock отвечает 304 только на запрос
с нужным `If-None-Match`, и отдельно проверяется, что заголовок действительно ушёл.

### Исходы опроса

`PollResult` это sealed-интерфейс с пятью вариантами: `Updated` с датой и новым ETag,
`NotModified`, `NotFound`, `RateLimited` с `Retry-After` и `Failed` с флагом `retryable`.
Обработчик разбирает его через `switch`, и компилятор проверяет полноту: добавлю новый
исход, сборка упадёт, пока я не разберу его везде.

Разные исходы по-разному влияют на ссылку. 404 отключает её сразу: репозиторий удалён
и обратно не появится, повтор только съест лимит. Сетевой сбой и 5xx повторяются в тике
с задержкой, а после пяти неудачных тиков подряд ссылка отключается. Лимит GitHub только
сдвигает время следующей проверки и счётчик неудач не трогает.

Здесь я поймал баг. Сначала 403 на лимите был обычным `Failed`, и без токена, где лимит
60 запросов в час, сервис за несколько минут выключал все подписки сам себе. Ошибка
внешнего API и ошибка конкретного ресурса это разные вещи, и когда они лежат в одном
типе, страдают подписки, которые ни в чём не виноваты.

Ответ разбирается через `exchange`, а не `retrieve`: `retrieve` бросает исключение на
4xx и 5xx, и ветки со статусами стали бы недостижимы. Второй баг был тут же. У `exchange`
есть перегрузка с булевым аргументом, и я передавал `false`, думая, что это отключает
разбор статусов. На самом деле это `close`, и ответ просто не закрывался: планировщик
тёк соединениями. Нашёл тестом, который считает вызовы `close()` на ответе.

### Задержка между повторами

Если внешний сервис лёг, повторять каждые 100 мс значит добивать его. Задержка
удваивается: 1с, 2с, 4с, с потолком в минуту и случайным разбросом ±25%, иначе все
клиенты, упавшие в одну секунду, повторят запрос тоже в одну секунду.

`BackoffRetry` написан руками, хотя в проде это делает Resilience4j. Политика повторов
это место, где ошибка дорого стоит, и мне хотелось видеть её в коде, а не в конфиге.
Сон вынесен в интерфейс `Sleeper`, поэтому тесты не ждут по-настоящему. Удвоение идёт
циклом с проверкой потолка, а не сдвигом: при большом числе попыток сдвиг уходил в минус
и ронял генератор джиттера. На `InterruptedException` повторы прекращаются и флаг
прерывания восстанавливается.

### Таймауты

У `SimpleClientHttpRequestFactory` таймаутов по умолчанию нет. Один зависший запрос
занял бы поток планировщика навсегда, и сервис выглядел бы живым, ничего не делая.
Стоят 3 секунды на соединение и 5 на чтение. В тесте WireMock отвечает через 3 секунды,
а клиент с таймаутом 200 мс возвращает `Failed` заметно раньше. Тело ответа читается
не больше мегабайта, на это тоже есть тест.

### fixedDelay, а не fixedRate

`fixedRate` отсчитывает интервал от начала предыдущего запуска: если обход занял дольше
интервала, следующий стартует сразу и запуски накладываются ровно тогда, когда внешний
API и так медленно отвечает. `fixedDelay` отсчитывает от окончания.

Очередь на тик берётся запросом «активные ссылки, не проверявшиеся дольше порога»,
давно не проверенные первыми, чтобы ни одна не голодала. Из базы берутся только id,
сущность перечитывается уже внутри своей транзакции. Размер пачки ограничен, под запрос
в миграции есть индекс по `(active, last_checked_at)`.

### Транзакция на ссылку

Транзакцию открывает `LinkUpdateProcessor` на каждую ссылку отдельно, с `REQUIRES_NEW`.
Одной транзакцией на тик ошибка на девятой ссылке откатила бы результат первых восьми.
И держать транзакцию открытой на время сетевого запроса это верный способ исчерпать пул
соединений к базе. Процессор отдельный бин, а не приватный метод, потому что
`@Transactional` работает через прокси. Исключение на одной ссылке ловится в цикле обхода
и не останавливает остальные.

Уведомление отправляется после коммита, а не внутри транзакции. Раньше было внутри, и
если `Notifier` бросал исключение, откатывались и новый ETag с датой, а то же обновление
уходило заново на каждом тике. Сейчас сбой доставки теряет уведомление, но не дублирует
его. В проде на этом месте стоял бы transactional outbox.

### Уведомление ровно один раз

На первой проверке уведомление не уходит: подписчик только что добавил ссылку и не ждёт
сообщения о том, что было до него. Дальше решение принимает сама сущность в `applyUpdate`,
и сравнение там строго «позже», через `isAfter`. На «не равно» дата старее сохранённой
дала бы ложное уведомление об обновлении в прошлое.

### Уникальность в базе

Сервис перед вставкой проверяет, что такой подписки ещё нет, но два одновременных запроса
пройдут проверку оба. Поэтому в миграции стоит уникальное ограничение на
`(subscriber, owner, repository)`, а нарушение уникальности превращается в 409.

### Мелочи, на которых ловят

- Разбор ссылки идёт по правилам GitHub: владелец до 39 знаков без точек, репозиторий
  до 100. Свободная регулярка пропускала `..` в путь запроса и имена длиннее колонки.
- `GitHubProperties` это record, и его `toString()` печатал токен целиком при ошибке
  привязки конфигурации. Замаскирован.
- Время берётся из бина `Clock`, в тестах его можно подменить.

## Тесты

| Класс | Что проверяет |
|---|---|
| GitHubUrlTest | разбор ссылки: www, слэш и `.git` на конце, чужой домен, `..`, длинные имена |
| TrackedLinkTest | когда уведомлять и когда молчать, счётчик неудач, отключение ссылки |
| BackoffRetryTest | число попыток, рост задержки, потолок, прерывание потока |
| GitHubClientTest | на WireMock: 304 по ETag, 404, 429, 403 на лимите, 500, битый JSON, таймаут, закрытие ответа |
| GitHubPropertiesTest | токен не попадает в `toString()` |
| LinkApiWebTest | HTTP: 201, 400 на кривой URL, 409 на дубликат, чужая ссылка 404 |
| UpdateCheckerTest | одна сломанная ссылка или упавший `Notifier` не останавливают тик |
| UpdateFlowIntegrationTest | сквозной сценарий на H2: добавили ссылку, обошли, пришло одно уведомление |

Внешний API подменён WireMock, настоящим HTTP-сервером, а не моком. Мок вернул бы то,
что я ему велел. WireMock отдаёт реальные коды и заголовки, умеет держать паузу и считать
пришедшие запросы, поэтому на нём проверяется, ушёл ли `If-None-Match`, сколько раз
клиент реально сходил на сервер и что будет на сценарии «сначала 503, потом 200».

Интеграционный тест поднимает контекст на H2 с теми же миграциями Liquibase, что и прод.
Планировщик в профиле `test` фактически выключен, интервал выставлен в час, а обход
запускается вручную через `runOnce()`.

## Что не сделано

- Уведомления только в лог. Telegram и Kafka заложены интерфейсом `Notifier`, второй
  реализации нет.
- Аутентификации нет, подписчик это строка в запросе.
- Один репозиторий с десятью подписчиками опрашивается десять раз. Кэшем это не лечится,
  у каждого свой ETag, нужна отдельная таблица репозиториев.
- На лимите сервис сдвигает проверку, но не ждёт до сброса по `X-RateLimit-Reset`.
- Планировщик рассчитан на один экземпляр, распределённой блокировки нет.
- Обход внутри тика последовательный.
