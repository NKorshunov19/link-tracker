# link-tracker

Сервис следит за репозиториями на GitHub и уведомляет подписчиков о новых изменениях.
Задача взята по мотивам учебного проекта Т-Банка «Link Tracker» — она хороша тем, что
почти вся сложность здесь не в бизнес-логике, а в работе с ненадёжным внешним API.

**Стек:** Java 21, Spring Boot 3.5, PostgreSQL, Liquibase, RestClient, Caffeine,
JUnit 5, WireMock, Docker, GitHub Actions.

## Запуск

```bash
docker compose up --build      # приложение вместе с базой
mvn test                       # 43 теста, база и сеть не нужны
```

```bash
# добавить репозиторий на отслеживание
curl -X POST localhost:8080/api/links -H 'Content-Type: application/json' \
  -d '{"subscriber":"nikita","url":"https://github.com/spring-projects/spring-boot"}'

curl 'localhost:8080/api/links?subscriber=nikita'
```

## Инженерные решения

### Условные запросы: ETag вместо лишнего трафика

У GitHub лимит 60 запросов в час без токена и 5000 с токеном. Если проверять сотню
репозиториев раз в полминуты, лимит кончится за минуты.

Поэтому ETag прошлого ответа сохраняется и в следующий раз уходит в заголовке
`If-None-Match`. На неизменившийся репозиторий GitHub отвечает `304 Not Modified` —
такой ответ не тратит лимит и не тянет тело. Тест `sendsConditionalRequestAndHandlesNotModified`
проверяет, что заголовок действительно уходит, а 304 не считается ошибкой.

### Не всякий сбой стоит повторять

`403` при исчерпании лимита и `500` — временные, их повторяем. `404` — постоянный:
репозиторий удалён и обратно не появится, повтор только съест лимит. Битый JSON —
тоже постоянный, он придёт таким же.

Это различие выражено в типе: `PollResult.Failed` несёт флаг `retryable`, и политика
повторов смотрит только на него. Тесты `doesNotRetryOnNotFound` и `retriesOnServerError`
проверяют реальное число запросов к серверу — 1 против 3.

### Экспоненциальная задержка с джиттером

Если внешний сервис лёг, повторять каждые 100 мс — значит добивать его. Задержка
удваивается: 1с, 2с, 4с. Джиттер ±25% нужен, чтобы все клиенты, упавшие в одну секунду,
не повторили запрос тоже в одну секунду — иначе получается thundering herd.

Написано руками и покрыто тестами намеренно, включая корректную обработку прерывания
потока. В продакшене это делает Resilience4j, но политика повторов — та часть,
где ошибки дороги, и хотелось, чтобы она была явной и проверяемой.

### Таймауты — не мелочь

По умолчанию у HTTP-клиента их нет вовсе. Один зависший запрос занял бы поток
планировщика, и остальные репозитории перестали бы проверяться. Тест
`slowResponseIsCutOffByTimeout` поднимает сервер, который отвечает через 3 секунды,
и проверяет, что клиент не стал столько ждать.

### fixedDelay, а не fixedRate

`fixedRate` отсчитывает интервал от **начала** предыдущего запуска: если обход занял
дольше интервала, следующий стартует сразу, и запуски начинают накладываться.
`fixedDelay` отсчитывает от **окончания**, поэтому перегрузки внешнего API не будет,
даже если GitHub отвечает медленно.

### Транзакция на ссылку, а не на весь обход

Каждая ссылка обрабатывается в собственной транзакции (`REQUIRES_NEW`). Одной
транзакцией на весь тик ошибка на девятой ссылке откатила бы результат первых восьми.
И держать транзакцию открытой всё время сетевых запросов — верный способ исчерпать
пул соединений к базе.

### Уведомление ровно один раз

На первой проверке уведомление не шлётся: подписчик только что добавил ссылку и не ждёт
сообщения о том, что было до него. Дальше сравнение строго по «позже», а не «не равно» —
если API вернёт более старую дату, повторного уведомления не будет.

### Sealed-интерфейс вместо null и исключений

`PollResult` — sealed-интерфейс с тремя наследниками: `Updated`, `NotModified`, `Failed`.
Три исхода здесь равноправны, и возвращать `null` или бросать исключение на каждый
из них было бы неверно. Компилятор знает полный список наследников, поэтому `switch`
по нему проверяется на полноту — забыть ветку не получится, сборка не пройдёт.

## Тесты

43 теста, `mvn test` проходит без Docker и без доступа в интернет.

Внешний API подменён **WireMock** — настоящим HTTP-сервером, а не моком. Разница
принципиальная: мок вернул бы то, что я ему велел, и проверил бы только мою же выдумку.
WireMock отдаёт реальные коды и заголовки и умеет держать паузу, поэтому на нём
проверяются вещи, которые на моках не проверишь: условный запрос, обработка 304,
поведение при таймауте, сценарий «сначала 503, потом 200».

## Что бы я сделал дальше

- Разделить на два сервиса, как в оригинальном проекте: опрашивающий и уведомляющий,
  с обменом через Kafka. Сейчас `Notifier` — интерфейс с одной логирующей реализацией
  именно для того, чтобы это разделение не потребовало трогать логику проверки.
- Добавить Telegram-бота как вторую реализацию `Notifier`.
- Поддержать Stack Overflow вторым источником.
- Учитывать заголовок `X-RateLimit-Reset` и притормаживать до его наступления,
  а не просто повторять.
- Вынести отслеживание в очередь с приоритетом: сейчас все ссылки проверяются
  с одинаковой частотой независимо от того, как часто они реально меняются.
